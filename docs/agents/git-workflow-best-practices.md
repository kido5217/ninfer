# Git workflow for AI coding agents: primary-source best practices

Scope: how agent-authored changes should flow through git in a protected, PR-only repository like this one (solo maintainer plus AI agents). Research date: 2026-09-15.

Method: primary vendor/standard documents read live on 2026-09-15 (GitHub Docs and Blog, agents.md, OpenAI Codex, Anthropic Claude Code, Cursor, Google Jules and Gemini CLI, git-scm, Conventional Commits). Secondary posts were used for discovery only. Where primary sources disagree or are silent, that is stated explicitly rather than smoothed over.

## 1. Git workflow for agent-authored changes

- **Branch per task is the vendor default.** GitHub Copilot "can only work on one branch at a time and can open exactly one pull request to address each task", and "can only push to branches it created" ([about-cloud-agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent), [GitHub Blog](https://github.blog/news-insights/product-news/github-copilot-meet-the-new-coding-agent)). Cursor cloud agents "work on a separate branch, then push changes to your repo for handoff" ([Cursor Cloud Agents](https://cursor.com/docs/cloud-agent)). Codex cloud has you "open a pull request when the work is ready" ([Codex cloud](https://developers.openai.com/codex/cloud)). Jules publishes a branch or PR from the VM it worked in ([Jules: Reviewing code changes](https://jules.google/docs/code/)). Claude Code's documented finishing step is "commit with a descriptive message and open a PR" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices), [Common workflows](https://code.claude.com/docs/en/common-workflows)).
- **PR-only on the default branch is the documented enforcement layer, and it does not require approvals.** GitHub: "You can require that all changes to the target branch be associated with a pull request. The pull request doesn't necessarily have to be approved, but it must be opened" ([Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)). GitHub's own starter rulesets for the default branch both include the `pull_request` rule ([github/ruleset-recipes](https://github.com/github/ruleset-recipes)).
- **The vendor review gate is a human.** GitHub enforces that "Pull request authors cannot approve their own pull requests", and if you assigned Copilot to an issue you also cannot approve the resulting PR ([Approving a pull request with required reviews](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews)). The Copilot launch post: "the developer who asks the agent to open a pull request *cannot* be the one to approve it ... any 'required reviews' rule you have set up in your repository will be honored" ([GitHub Blog](https://github.blog/news-insights/product-news/github-copilot-meet-the-new-coding-agent)). OpenAI states code review "doesn't replace tests, branch protections, or required approvals" ([Codex code review](https://developers.openai.com/codex/third-party/github)). Anthropic: "Review Claude's generated PR before submitting" ([Common workflows](https://code.claude.com/docs/en/common-workflows)).
- **Small, single-purpose tasks are what the vendors document.** GitHub's guidance: tasks should be "clear, well-scoped" with acceptance criteria; "complex and broadly scoped tasks", production-critical, security, and ambiguous work are listed as things to do yourself ([Best practices for using Copilot on tasks](https://docs.github.com/en/copilot/tutorials/cloud-agent/get-the-best-results)). Copilot sessions have a hard 59-minute cap, and GitHub advises "breaking the work into smaller, more focused tasks" ([about-cloud-agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent)). Conventional Commits: "Go back and make multiple commits whenever possible" ([Conventional Commits 1.0.0](https://conventionalcommits.org/en/v1.0.0/)). Cursor: start a new conversation when "you've finished one logical unit of work" ([Cursor best practices](https://cursor.com/blog/agent-best-practices)).
- **Conventional Commits is a spec plus a GitHub-supplied enforcement recipe, not a vendor agent mandate.** The spec defines `<type>[scope]: <description>` with `fix`/`feat` and optional additional types ([spec](https://conventionalcommits.org/en/v1.0.0/)). GitHub's "PRs & conventional commits" starter ruleset implements it as a `commit_message_pattern` regex restricted to `^(build|chore|ci|docs|feat|fix|perf|refactor|revert|style|test)...` ([github/ruleset-recipes](https://github.com/github/ruleset-recipes)). The agent vendor docs themselves only require descriptive/clear commit messages ([Claude Code best practices](https://code.claude.com/docs/en/best-practices), [Cursor best practices](https://cursor.com/blog/agent-best-practices)); Copilot "automates branch creation, commit message writing, and pushing" without naming a format ([about-cloud-agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent)).
- **No primary source authorizes an agent to merge its own change.** All cloud-agent docs end at "open a PR"; GitHub's ruleset recipe requires the last push be approved (`require_last_push_approval: true`) ([recipes](https://github.com/github/ruleset-recipes)); and GitHub blocks author self-approval ([docs](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews)). Note the asymmetry: with **zero** required approvals the platform gate is not review-based at all — GitHub describes such configurations as "repositories that use pull requests as a record of changes rather than to gate on approvals" ([Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)).

## 2. AGENTS.md conventions

- **The standard is intentionally minimal.** agents.md is "a simple, open format for guiding coding agents", "a README for agents"; there are no required fields and any headings work ([agents.md](https://agents.md/)). Recommended content: project overview, build and test commands, code style, testing instructions, security considerations, plus "commit messages or pull request guidelines ... anything you'd tell a new teammate". Nested files are supported and "the closest AGENTS.md to the edited file wins". It is stewarded by the Agentic AI Foundation under the Linux Foundation, and emerged with OpenAI Codex, Amp, Jules, Cursor, and Factory ([agents.md](https://agents.md/)).
- **OpenAI Codex.** Discovery starts at the global `~/.codex` file, then walks project directories; `AGENTS.override.md` beats `AGENTS.md`, one file per directory, concatenated root-down so closer files override, with a 32 KiB combined cap (`project_doc_max_bytes`) and configurable fallback filenames ([Custom instructions with AGENTS.md](https://developers.openai.com/codex/guides/agents-md)). Review guidance belongs in a `## Code Review Rules` section in the AGENTS.md closest to the governed code ([same page](https://developers.openai.com/codex/guides/agents-md), [Codex code review](https://developers.openai.com/codex/third-party/github)).
- **Anthropic Claude Code reads `CLAUDE.md`, not `AGENTS.md`.** "If your repository already uses `AGENTS.md` for other coding agents, create a `CLAUDE.md` that imports it" (`@AGENTS.md`) or symlink it ([Claude memory](https://code.claude.com/docs/en/memory)). Guidance: target under 200 lines, concrete verifiable rules ("Run `npm test` before committing"), consistent non-contradictory rules, prune when ignored — "Bloated CLAUDE.md files cause Claude to ignore your actual instructions"; keep frequently changing or tutorial content out ([memory](https://code.claude.com/docs/en/memory), [best practices](https://code.claude.com/docs/en/best-practices)).
- **Cursor supports `AGENTS.md` directly** at the root and in subdirectories, with nested instructions combined and "more specific instructions taking precedence" ([Cursor rules](https://cursor.com/docs/context/rules)). Cursor's rule-authoring guidance doubles as AGENTS.md guidance: keep rules focused and actionable, split large rules, reference canonical files instead of copying, and avoid "copying entire style guides", "documenting every possible command", rare edge cases, and duplicated codebase content; keep rules under 500 lines ([rules](https://cursor.com/docs/context/rules), [best practices](https://cursor.com/blog/agent-best-practices)).
- **Google and GitHub.** Gemini CLI uses `GEMINI.md` by default but `context.fileName` accepts a list such as `["AGENTS.md", "CONTEXT.md", "GEMINI.md"]`, and it loads files hierarchically with `@file` imports ([Gemini CLI docs](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/gemini-md.md)). Jules "automatically looks for a file named AGENTS.md in the root of your repository" ([Jules getting started](https://jules.google/docs/)). GitHub Copilot supports "one or more `AGENTS.md` files, stored anywhere within the repository", nearest file wins, with a root `CLAUDE.md` or `GEMINI.md` as alternative, alongside `.github/copilot-instructions.md` and path-specific `.github/instructions/**/*.instructions.md` ([GitHub Docs](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions)). GitHub's own generation prompt for instructions says they "must be no longer than 2 pages" and "must not be task specific" ([same page](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions)).

## 3. Branch protection and rulesets

- **What GitHub documents for protected branches.** Available classic settings: require PR reviews; require status checks ("strict" = branch must be up to date, "loose" = not); require signed commits; require linear history (repository must allow squash or rebase merging); require deployments; lock branch; block force pushes and deletions (both are the default for any rule); restrict pushers; and "Do not allow bypassing the above settings" to apply restrictions to admins ([About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)).
- **GitHub's closest thing to a published baseline is its ruleset recipes repo** (pre-baked starter rulesets): "Branch protection best practices" = PR rule (2 approvals, last-push approval, code-owner review off, stale dismissal off) + required status checks + block deletion + block non-fast-forward; "PRs & conventional commits" = the same on `~DEFAULT_BRANCH` plus the commit-message pattern and an org-admin bypass actor ([github/ruleset-recipes](https://github.com/github/ruleset-recipes)). GitHub Docs itself documents behavior, not a single mandatory checklist.
- **Rulesets vs classic branch protection.** Only one classic rule can apply to a branch, while "multiple rulesets can apply to the same branch at the same time"; where rules overlap "the most restrictive version of the rule applies"; read-access users can view active rulesets "and lets auditors review repository protections without administrator access" ([About rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets), [Converting branch protections to rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/converting-branch-protections-to-rulesets)). GitHub provides a guided per-rule conversion that previews the resulting ruleset(s) and can preserve behavior; the one documented mapping exception is "Require conversation resolution before merging" ([Converting branch protections to rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/converting-branch-protections-to-rulesets)).
- **Solo maintainers must not require approvals they cannot obtain.** GitHub: "Pull request authors cannot approve their own pull requests" — a hard platform rule ([Approving a pull request with required reviews](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews)). A zero-approval required-PR configuration is explicitly valid ([Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)). The new ruleset setting "Require an additional approval for unattributed Copilot pull requests" (public preview, on by default) "has no effect if the ruleset requires zero approvals" ([same page](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)). Escape hatches exist but are ownership-sensitive: classic branch-protection bypass actors "may only be added ... when the repository belongs to an organization" ([About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)), while ruleset bypass lists cover repository admins, maintain/write roles, teams, GitHub Apps, and Dependabot, and support a "For pull requests only" mode that still forces a PR, creating "a clear trail of their changes in the pull request and audit log" ([Creating rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository)).
- **Required status checks need a real check first.** With required checks enabled, all must pass before merge; a ruleset's "require branches to be up to date" setting does nothing until you define a check, and GitHub warns that duplicate job names across workflows can produce ambiguous results and block PRs ([Creating rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository), [About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)).

## 4. Parallel agents and worktrees

- **git worktree is the isolation primitive.** "A git repository can support multiple working trees, allowing you to check out more than one branch at a time"; linked worktrees share refs but get their own `HEAD`/index, and `git worktree add` refuses to check out a branch that is already checked out elsewhere unless forced ([git-worktree](https://git-scm.com/docs/git-worktree)).
- **Anthropic: one worktree per session.** "Running each Claude Code session in its own worktree means edits in one session never touch files in another"; Claude Code isolates tool calls to the worktree, can branch subagents with `isolation: worktree`, creates them under `.claude/worktrees/` from the default branch by default, and documents the operational gaps: add `.claude/worktrees/` to `.gitignore`, carry gitignored files via `.worktreeinclude`, and install dependencies in each fresh checkout ([Run parallel sessions with worktrees](https://code.claude.com/docs/en/worktrees)). The Claude Code team's own guidance is "running 3–5 Claude sessions in parallel, each in its own git worktree", and `/batch` fans work out to worktree agents that "test its changes end to end, then put up a PR" independently ([Claude Code power user tips](https://support.claude.com/en/articles/14554000-claude-code-power-user-tips)).
- **OpenAI: one chat per worktree, with the same branch uniqueness rule.** "Worktrees let Codex run multiple independent chats in the same project without interfering with each other"; managed worktrees live under `$CODEX_HOME/worktrees`, start in detached HEAD (so they don't pollute branches), and support `.worktreeinclude` for gitignored setup files; "Git only allows a branch to be checked out in one place at a time" ([Codex worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees)).
- **Cursor: worktrees for parallel agents, configurable setup.** Cursor creates a separate checkout per agent so several can run "without conflicts"; `/worktree` isolates the rest of a chat, `/best-of-n` gives each model candidate its own worktree, and `.cursor/worktrees.json` can install dependencies and copy `.env` files into each worktree ([Cursor worktrees](https://cursor.com/docs/configuration/worktrees)). Cloud agents instead get their own VM and branch, so parallel cloud runs need no local worktrees ([Cursor Cloud Agents](https://cursor.com/docs/cloud-agent)).
- **Net practice: one agent = one branch = one worktree, and let the platform isolate cloud agents.** The documented conflicts are file collisions (solved by separate checkouts) and duplicate branch checkouts (refused by git); no primary source recommends two agents sharing a working tree or branch ([git-worktree](https://git-scm.com/docs/git-worktree), [Claude worktrees](https://code.claude.com/docs/en/worktrees), [Codex worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees)).

## 5. Direct-to-main vs PR-only, and auditability

- **No primary source recommends letting agents commit directly to the default branch.** Every cloud-agent path is branch-and-PR: Copilot "can only push to branches it created" ([GitHub Blog](https://github.blog/news-insights/product-news/github-copilot-meet-the-new-coding-agent)); Cursor pushes a branch for handoff ([Cursor Cloud Agents](https://cursor.com/docs/cloud-agent)); Codex is "review before you merge" ([Codex cloud](https://developers.openai.com/codex/cloud)); Jules publishes a branch/PR ([Jules](https://jules.google/docs/code/)); Claude Code's documented end state is a PR ([Common workflows](https://code.claude.com/docs/en/common-workflows)). Where direct pushes are possible (local CLI agents with repo credentials), the documented control is branch protection: Copilot works "in exactly the way you'd expect" under existing branch protections, and repository rules that Copilot cannot comply with block the agent unless it is added as a bypass actor ([GitHub Blog](https://github.blog/news-insights/product-news/github-copilot-meet-the-new-coding-agent), [about-cloud-agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent)).
- **Auditability is built from session logs, attribution, and signing.** Copilot session logs record "internal reasoning and the tools it used"; commits "are authored by Copilot, with the person who started the task listed as co-author. Each commit message includes a link to the session logs, so you can trace why a change was made during code review or an audit. Commits are signed and appear as 'Verified'"; sessions are shared repo-wide by default, and usage metrics cover PR outcomes ([Managing agent sessions](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents), [about-cloud-agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent)). Copilot commit signing removed its previous incompatibility with the "Require signed commits" rule ([changelog 2026-04-03](https://github.blog/changelog/2026-04-03-copilot-cloud-agent-signs-its-commits/)). GitHub documents signature verification as proving origin and integrity, including for bots ([About commit signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification)).
- **Other vendors expose equivalent traces.** Cursor attaches screenshots/videos/logs to the PR and exposes transcripts, run events, and environment details via its Cloud MCP ([Cursor Cloud Agents](https://cursor.com/docs/cloud-agent)); Jules shows a real-time activity feed, diffs, and a final summary with branch and commit message, with Jules as commit author ([Jules: Reviewing code changes](https://jules.google/docs/code/)); Codex exposes task logs and a standard PR review ([Codex cloud](https://developers.openai.com/codex/cloud), [Codex code review](https://developers.openai.com/codex/third-party/github)).
- **What auditability does not prove.** OpenAI: review rules "guide Codex; they don't replace tests, branch protections, or required approvals" ([Codex code review](https://developers.openai.com/codex/third-party/github)). Signing proves the commit came from the platform's key, not that the change is correct ([changelog](https://github.blog/changelog/2026-04-03-copilot-cloud-agent-signs-its-commits/)). Local CLI agents carry the maintainer's own credentials and git identity; no vendor document reviewed here adds provenance beyond what that identity and the PR history already provide.

## Implications for this repo

Current setup: `master` protected (PR required, 0 approvals, force pushes/deletions blocked, admins enforced, linear history required), AGENTS.md requires a branch + PR, no CI.

- **The 0-approval PR gate is a documented configuration, and it avoids the solo-maintainer deadlock.** GitHub explicitly allows a required PR "that doesn't necessarily have to be approved" and describes 0-approval rulesets as "pull requests as a record of changes rather than to gate on approvals" ([Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)). Raising required approvals above 0 would block the sole maintainer, since author self-approval is impossible ([Approving a pull request with required reviews](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews)); a second writer or a ruleset bypass actor would be required first.
- **Be explicit that "human merges" is policy, not enforcement.** With 0 required approvals the platform does not gate merges on review, only on PR existence (plus checks when configured) ([rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)). If an agent credential with write access could merge its own PR, only the AGENTS.md rule prevents it; no vendor feature reviewed here forbids author-merges beyond the approval requirement ([same page](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)).
- **Candidate: convert the classic rule to a ruleset** using GitHub's guided conversion, which preserves behavior and adds read-access visibility of the active rules plus multiple-ruleset layering ([Converting branch protections to rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/converting-branch-protections-to-rulesets)). If bypass flexibility ever matters, ruleset bypass lists are documented for repository admins and support "For pull requests only" with an audit trail; classic bypass actors are org-only ([Creating rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository), [About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)).
- **Linear history is required on `master` (applied 2026-09-15); require status checks only after CI exists.** Linear history matches the current rebase-merge practice and needs only squash/rebase merging enabled ([About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)). There is no CI today, and a required check must exist before it can be required; GitHub also warns to keep job names unique across workflows ([Creating rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository), [About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)). GitHub's recipe combines PR + required checks + no force pushes + no deletions ([ruleset-recipes](https://github.com/github/ruleset-recipes)).
- **Candidate: enforce the existing Conventional Commit style with a ruleset metadata restriction**, per GitHub's "PRs & conventional commits" recipe ([ruleset-recipes](https://github.com/github/ruleset-recipes)). Caveats from the docs: metadata restrictions "are not intended to replace security measures such as requiring code review", and a squash merge requires every commit on the branch to satisfy the pattern ([Creating rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository)). Keeping it as an AGENTS.md instruction is equally vendor-sanctioned ([agents.md](https://agents.md/) lists commit/PR guidelines as AGENTS.md content).
- **Candidate: signed commits only once every commit source signs.** Copilot cloud agent now signs and works under "Require signed commits" ([changelog](https://github.blog/changelog/2026-04-03-copilot-cloud-agent-signs-its-commits/)), but GitHub documents that unsigned commits on a PR head branch can block a squash merge, requiring rewrite + force push, and that Rebase-and-Merge does not verify head-branch signatures ([About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [About commit signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification)). Local agent commits therefore need local signing configured first.
- **Candidate: add a `CLAUDE.md` that imports `@AGENTS.md` if Claude Code is used**, since Claude Code reads `CLAUDE.md` and not `AGENTS.md` ([Claude memory](https://code.claude.com/docs/en/memory)); Gemini CLI users would set `context.fileName` to include `AGENTS.md` ([Gemini CLI](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/gemini-md.md)). Copilot, Codex, Cursor, and Jules read `AGENTS.md` as-is.
- **Candidate: keep AGENTS.md short and link long detail from `docs/`.** Claude targets <200 lines and ignores bloated files; Cursor targets ≤500 lines with no style-guide copies; Codex caps combined instructions at 32 KiB; GitHub's generated instructions target ≤2 pages and no task-specific rules ([memory](https://code.claude.com/docs/en/memory), [Cursor rules](https://cursor.com/docs/context/rules), [Codex AGENTS.md](https://developers.openai.com/codex/guides/agents-md), [GitHub instructions](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions)).
- **Candidate: for local parallel agents, use one worktree/branch per agent**, with `.claude/worktrees/` gitignored and `.worktreeinclude` for local-only files if Claude Code is used ([Claude worktrees](https://code.claude.com/docs/en/worktrees)); the same `.worktreeinclude` convention exists for Codex ([Codex worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees)).
- **If Copilot cloud agent is enabled, no approval-config change is needed.** The extra-approval-for-unattributed-Copilot setting is a no-op at zero approvals, and rules Copilot cannot comply with block the agent until it is a bypass actor ([Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets), [about-cloud-agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent)).

### Conflicts and gaps in the primary sources

- **AGENTS.md vs CLAUDE.md is a real split:** agents.md's ecosystem list does not include Claude Code ([agents.md](https://agents.md/)), and Anthropic states plainly that Claude Code reads `CLAUDE.md`, not `AGENTS.md` ([memory](https://code.claude.com/docs/en/memory)). A single-file setup is not natively portable to Claude Code without an import or symlink.
- **No vendor mandates Conventional Commits** in its agent documentation; the only primary endorsement found is GitHub's optional ruleset recipe ([ruleset-recipes](https://github.com/github/ruleset-recipes)).
- **No primary source gives a mechanism to stop an agent that has merge credentials from merging its own PR when 0 approvals are required** beyond the human-only rule in AGENTS.md; the platform controls documented are PR requirement, checks, approvals, and signing, not author-based merge blocking ([Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)).
- **GitHub Docs publishes behavior and recipes, not one prescriptive branch-protection baseline**; the closest primary recommendation is the "Branch protection best practices" starter ruleset in GitHub's own repository ([github/ruleset-recipes](https://github.com/github/ruleset-recipes)).
